# ADR-007 — Row Level Security con SET LOCAL en Neon Serverless

- **Status**: IMPLEMENTED ✅ (Fase 13D, 2026-04-06 — commit `0ada843`)
  · **PARCIALMENTE CORREGIDO por [ADR-044](ADR-044-rls-fail-closed-por-defecto.md) (2026-08-15)**
- **Author**: arch-agent
- **Criticality**: SECURITY — defense-in-depth layer over ADR-004 application-level companyId checks

> ## ⚠️ CORRECCIÓN 2026-08-15 — leer ANTES de citar este ADR
>
> Este ADR afirmaba que olvidar `withCompanyContext` es **fail-closed** (0 filas,
> sin fuga). **Es FALSO tal como está montado el sistema.** La app conecta como
> `neondb_owner`, que tiene **BYPASSRLS**: si el código nunca entra al wrapper, el
> rol efectivo nunca cambia a `authenticated`, las policies **no se evalúan** y la
> consulta ve **todo**. La omisión es **fail-OPEN**.
>
> Cobertura medida el 2026-08-15: `withCompanyContext` se usa en **14 archivos
> (~30 call-sites)** frente a **84 archivos con `$transaction`** → ≈15 % de las
> escrituras transaccionales y ≈0 % de las lecturas (que no viven dentro de
> `$transaction`).
>
> **Postura real vigente**: el aislamiento multi-tenant es **100 % aplicativo**
> (ADR-004 + ADR-041 `requireCompanyAction` + `requireCompanyPage`). La RLS es
> **defensa en profundidad PARCIAL**, activa solo dentro de esos ~30 call-sites.
>
> El plan para volverla realmente fail-closed, el orden de ataque por riesgo y la
> mitigación del «0 filas en silencio» están en **ADR-044**. Ningún hallazgo de
> auditoría puede cerrarse con el argumento «lo cubre la RLS» mientras ADR-044 D-7
> siga abierto.

## Context

ContaFlow runs on Neon serverless with PgBouncer in **transaction mode**. This means:
- Session-level `SET` commands (`SET app.current_company_id = '...'`) do NOT survive the pool — each query may land on a different connection.
- Session-level advisory locks (LL-005) are also unusable for the same reason.

RLS was planned post-Fase 17 to add a database-level enforcement layer so that even if application code omits `companyId` from a query, the DB policy rejects the cross-tenant access.

## Decision

**Use `set_config(key, value, is_local := true)` (= `SET LOCAL`) inside `prisma.$transaction`.**

`SET LOCAL` applies only for the duration of the current transaction, not the session. Since Neon's PgBouncer returns the connection to the pool at transaction end, `SET LOCAL` is automatically cleaned up at `COMMIT` or `ROLLBACK`. This makes it fully compatible with transaction-mode pooling.

### Canonical pattern

```typescript
// src/lib/prisma-rls.ts
export async function withCompanyContext<T>(
  companyId: string,
  tx: Prisma.TransactionClient,
  fn: (tx: Prisma.TransactionClient) => Promise<T>
): Promise<T> {
  if (!companyId) {
    throw new Error("withCompanyContext: companyId no puede estar vacío");
  }
  // Fix A1 (ADR-007-addendum): neutraliza el BYPASSRLS de neondb_owner
  await tx.$executeRaw`SET LOCAL ROLE authenticated`;
  // is_local=true → equivalent to SET LOCAL — cleared at end of transaction
  await tx.$executeRaw`SELECT set_config('app.current_company_id', ${companyId}, true)`;
  return fn(tx);
}
```

Every domain `$transaction` block must wrap its body with `withCompanyContext`:

```typescript
await prisma.$transaction(async (tx) =>
  withCompanyContext(companyId, tx, async (tx) => {
    // queries here execute under RLS policy
  })
);
```

### Database policies

RLS is enabled on all 14 domain tables (ampliado a 88 tablas — ver addendum, fase A1-bis). The policy reads the transaction-local parameter:

```sql
-- Example: applied to every domain table (fail-closed — la implementación real)
ALTER TABLE "BankTransaction" ENABLE ROW LEVEL SECURITY;
CREATE POLICY company_isolation ON "BankTransaction"
  USING      ("companyId" = current_setting('app.current_company_id', true));
-- + WITH CHECK idéntico desde 20260611_rls_force_with_check
```

> **Corrección (hallazgo externo ADR — fail-closed).** La versión borrador de este
> ADR proponía un escape `OR current_setting(...) IS NULL OR ... = ''` para que
> migraciones/admin funcionaran sin contexto. **Ese escape nunca se implementó** y
> sería *fail-open*: una query bajo `authenticated` sin `withCompanyContext` vería
> filas de TODOS los tenants — justo el escenario que la RLS debe blindar. La
> migración real (`20260406110000_fase13d_rls_company_isolation`) y `ADR-007-rls-row-level-security.md`
> ya usan la policy sin escape. Con `missing_ok = true`, si falta el contexto
> `current_setting` devuelve NULL y `"companyId" = NULL` evalúa a NULL → la fila
> **no** es visible (*fail-closed*, 0 filas). Migraciones/admin no necesitan el
> escape porque corren bajo `neondb_owner` (BYPASSRLS).
>
> **⚠️ Alcance de esa corrección (precisado por ADR-044, 2026-08-15).** Lo anterior
> solo describe el caso «entré al wrapper pero falta el `set_config`» — que es
> imposible en la práctica, porque el wrapper hace `SET LOCAL ROLE` y `set_config`
> de forma atómica. El caso real de omisión es **«nunca entré al wrapper»**: el rol
> sigue siendo `neondb_owner` con BYPASSRLS, las policies **no se evalúan** y la
> consulta ve todo. Eso es **fail-OPEN**. `FORCE ROW LEVEL SECURITY` no lo evita:
> FORCE somete al *dueño* de la tabla, pero el atributo BYPASSRLS del rol efectivo
> siempre gana. Ver ADR-044 §2 (incluye la prueba empírica y la consulta de
> verificación) y ADR-044 D-4 (policies que **lanzan excepción** en vez de filtrar).

## Rejected alternatives

| Alternative | Reason for rejection |
|---|---|
| `SET app.current_company_id = '...'` (session-level) | Does not survive PgBouncer transaction mode — value leaks across requests (LL-005 analogue) |
| Neon direct connection for all queries | Defeats the purpose of the pooler; latency +40ms per query |
| Application-only enforcement (ADR-004) | Single layer — if one query misses `companyId`, data leaks. RLS is a mandatory second layer |
| Supabase RLS with `auth.uid()` | Supabase-specific, not available on Neon |

## Consequences

- **Positive**: Defense-in-depth — a bug in application code that omits `companyId` is still blocked at DB level **only inside the ~30 `withCompanyContext` call-sites**; outside them there is no DB-level protection (ADR-044 §2)
- **Positive**: `SET LOCAL` is transaction-scoped → zero risk of cross-request contamination in the pool
- **Negative (CORREGIDO 2026-08-15 — ADR-044)**: Olvidar `withCompanyContext` **NO** es fail-closed. El rol efectivo sigue siendo `neondb_owner` (BYPASSRLS), las policies no se evalúan y la consulta **ve todos los tenants**: es **fail-OPEN**. La única barrera real en ese caso es el filtro aplicativo `companyId` de ADR-004. El texto anterior de esta viñeta («la policy usa NULL y devuelve 0 filas, fail-closed, no leak») era **falso** y se citó como control compensatorio en auditorías previas: releerlas bajo ADR-044 §3
- **Negative**: Las lecturas de la app no viven dentro de `$transaction`, así que **ninguna** pasa hoy por el contexto RLS (≈0 % de cobertura en lectura)
- **Operational rule**: `withCompanyContext` sigue siendo obligatorio en todo `prisma.$transaction` que toque una tabla de dominio — y ahora también en todo SQL crudo sobre tablas tenant (ADR-044 D-8.2). Migraciones y scripts de administración corren fuera de `$transaction` y quedan exentos
- **Roadmap**: el estado objetivo (rol de login sin BYPASSRLS + cliente admin explícito para los flujos no-tenant) está definido en ADR-044 D-7. Hasta entonces, la afirmación pública sobre RLS debe ser la de ADR-044 §3
